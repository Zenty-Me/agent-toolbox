# 概念优先的教程改写

目标是让读者理解知识并能迁移使用。不能把“代码太多”的反馈仅处理成增加“选读”“可跳过”标签，也不能删掉代码后只剩结论清单。

## 确定本次范围

先读目标章节、课程导航和必要的相邻章节，确认读者已学什么、后续需要什么。利用现有上下文选择样章；用户给出截图时，优先选择截图所在章。

本 skill 跨技术领域复用，不把机器学习课程的术语、固定章节顺序或公式形式强加给其他技术。数据库、网络和系统教程可以用一次真实查询、请求或故障追踪贯穿概念；必要代码也包括 SQL、配置与命令，先说明执行前提、状态变化和可观察结果。

当用户明确要求“先做一章，满意后再改其他章节”，只交付这一章和必要配套素材，继续在同一章上迭代；是否满意由用户决定。用户接受样章前，不批量修改其他章节或全局阅读路线。明确记录反馈形成的写作偏好，更新本 skill；不要把某一章的代码数量或知识范围推广成所有章节的硬要求。

用户明确认可样节并授权推广后，继续完成已授权的其他章节，无需逐章重复确认。当前已确认的尺度见 [精简讲解样例](references/concise-example.md)：借鉴它解释概念的分寸，不照搬其主题、四个标题或字数。

## 逐段决定代码去留

从学习目的判断，不靠“验证”“训练”等关键词批量删除：

| 内容的作用 | 处理方式 |
| --- | --- |
| 只是确认公式、比较解析梯度与数值梯度、扫描参数或打印相同结果 | 通常直接删除，改为一个可复核的手算例子及解释 |
| 绘图、排版、计时、结果汇总等展示代码 | 删除读者不需要学习的实现；确有帮助的图可生成静态素材插入正文 |
| 训练循环、模型前向、张量形状变化、必要的数据处理等本章核心技能 | 保留最小完整实现，先解释输入、输出、关键步骤及为什么这样做 |
| 调试方法本身就是学习目标，例如梯度检查、掩码测试或恢复训练 | 保留能暴露错误的最小实验，说明观察什么、如何据此判断 |
| 超出当前目标的证明、算法变体和优化技巧 | 从当前章节移出，等读者在真实案例中遇到问题时再引入；案例里只补解决当前问题所需的最少概念 |

数学概念不要求每节附代码。每段保留代码都应承担独立、具体的学习作用；去掉装饰性输出、重复实现和仅用于“对答案”的工程细节。

## API 说明与逐节代码注释

概念优先不省略必要的接口用法。常用 API 首次出现时，在调用附近用短段落、参数表或行内注释交代用途、关键参数、返回值及类型/形状，让读者能修改这个例子。区分导入的是包、模块、函数还是类；只展开当前任务用到的参数，以及会影响理解的默认行为，不复制整份 API 手册。核对项目所用版本与官方文档，不能仅按函数名猜语义。

每个包含代码的小节都要有必要的代码内注释，即使相关 API 已在前文讲过。注释覆盖本段任务、关键步骤、容易误读的参数或数据变化；正文解释原理，注释帮助读者沿代码理解执行过程。按语义块注释，不要求逐行翻译，也不设机械的注释数量或比例。导入、数据准备、训练、预测和评测段落都要检查，不能只给用户指出的那一段加注释。

对含多个关键动作的链式调用或嵌套表达式，必要时拆成有意义的中间变量，再在易错处注释。已经讲过的 API 重用时说明本次用途和新增用法即可；不用每节重讲完整接口。注释应解释有用的信息，例如 `replace=False` 表示抽样不重复、`stratify=y` 按标签分层划分；“调用函数”“打印结果”等机械复述不足以帮助阅读。

以读者能否回答“数据从哪里来、这几个参数怎样影响行为、结果交给哪一步、哪个边界容易用错”为审查标准。注释、正文和实际源码必须一致；合成数据的列名不能被描述为真实业务含义，检查成功也不能被夸大为已证明没有全部数据泄漏或模型泛化可靠。

## 用解释接替代码

用户要求“以文档教程为主”时，把章节正文作为完整的学习载体：概念、必要代码、预期结果和推理就近呈现，读者不必在 README、示例源码和练习目录之间往返才能理解主线。独立源码用于运行与查阅，练习用于巩固；不能把“补完 TODO、通过测试”设为默认阅读流程。目录优先链接章节文档，工具清单和配套代码入口放到需要它们的位置。先修正教学组织方式，不能只增加正文篇幅或给原有流程加上“选读”标签。

围绕读者的问题组织连续叙述：这个概念解决什么问题，量和符号各指什么，关系为何成立，在一个小例子中如何算出来，接下来在哪里用。按内容需要组织，不强制每节套同一组标题。

已确认的写作尺度是“让我明白，讲清楚就停”。“知识点不笼统、结构直观”不能被解释为面面俱到。优先用一个简单例子、一条主线和少量标题，讲到读者能解释当前概念并跟上下一步为止。

用户明确要求保留代码和运行结果时，二者应就近放在正文中；不能因为追求简洁而删除。围绕具体需求给出可运行的最小例子，用实际输出解释关键执行过程，首次出现的关键语法在使用处讲清；已有编程基础的读者无需反复学习通用基础知识。

正文直接进入知识点，不在章首堆放“目标、先修第几章、预计时长、完成标准”这类课程管理文字，也不写“保留哪些代码、删掉哪些演示”的编辑说明。学习路线集中在目录或指南；确有必要的依赖应在使用处具体说明缺少哪个概念，不能用含糊章号代替解释。设备、数据下载、文件覆盖等会影响实际运行的条件仍须保留在相关位置。用户指出一句冗余文字时，同时检查所在章的每个知识点：定义是否明确、例子是否算对、前提是否说清、公式与代码是否一致、首次使用是否得到解释；不能只删这一句话就宣布整章已经完善。全课程同类文案清理与逐知识点的内容核对是不同范围，交付时分别说明实际完成了哪些。

- 只展开当前问题必需的概念和中间步骤。相关名词清单、分布大全、完整证明和特殊边界留到实际需要时再讲，不为覆盖全面而塞进同一节。
- 先用简单例子说明，再给必要公式；公式就近解释，不再把同一内容重复成关系图、导航表、步骤表和多轮小结。
- 图、交互和自测按理解需要选择，不作为每节标配。短小节可直接结束，不强加学习目标、过关标准或长套题。
- 用户反馈繁琐时，应实际缩减旁支与重复内容，不只缩短句子或把长内容折叠隐藏。新的样节仍由用户确认；对已明确接受的样节，不重新索要确认。

长章可以有多个知识点，但每个知识点仍只围绕当前要解决的问题。不要把一整章硬压成四段，也不要给所有小节机械添加“是什么、为什么、怎么做”的空框架。标题标出概念或动作，正文用因果关系连接步骤。只有结论而没有必要中间步骤时要补；同一结论被图、表、回顾反复复述时要删。

解释代码时直接交代本段输入、关键操作和结果去向。保留会影响运行的条件与边界，不堆叠与当前任务无关的注意事项；历史实验输出改写为应观察的现象，不能将固定数字或“完全一致”当作读者运行必然得到的结果。

- 一次引入少量符号，说明形状、求和或平均、对数底数等会影响结果的约定。
- 用小整数、两三个类别或低维矩阵把关键步骤展开；例子要给出计算过程，不能只报答案。
- 类比之后回到准确含义，给出必要条件。例如“负梯度下降最快”指同一位置、相同欧氏步长下的一阶局部比较；它不保证任意学习率都下降。
- 将核心结论与高级推导区分开。主线章节不要把大量“选读”内容堆在末尾；把 SVD、ELBO、Hessian、KKT 等知识绑定到后续真实案例，在案例需要时再解释概念、公式和局限。
- 先给案例中的问题，再补它所需要的数学。案例结束后可以留下一个简短的“本次用到什么”回顾，但不要在前置章节提前展开整套理论。
- 不依赖未出现的 PyTorch API 来解释尚未学会的数学；必要的实现可以独立执行，并给出关键预期结果。
- 自测优先要求解释、预测变化、手算或定位错误；明确哪些是主线完成标准，哪些是方向相关练习。提供可核对的答案，避免“全部实验跑通”替代理解。

## 编辑 notebook 的约束

修改实际源文件。先检查代码依赖、来源映射、被引用的 cell ID/锚点、图片和章节链接。删除代码后同步清理“如下图”“运行后可见”“与上一个实验一致”等失去对象的句子。

一个 Markdown 单元可能同时包含上一段的结果解释和下一节的标题、公式或代码前提。替换前读完整个单元及相邻内容，保留下一节的入口；沿用现有编号，不能凭上下文猜编号。精简后检查标题顺序与正文中的小节引用。

改写过程说明放在交付报告，课程正文直接讲学习内容，避免反复写“删除了某代码”“不再打印某结果”。文件、源码和实验职责要统一，不能在讲义另写一套字段名或接口不相容的实现。

正文已有错误时直接修正对应解释，不只在开头加一句纠错后留下矛盾原文。核对示意数字与计算结果；分词 ID、模型输出等虚构例子须明确是示意，不能写成真实模型的固定行为。指向共享实现时，就近说明实际输入、返回值与关键参数，删去接口不一致的重复实现。

保留有用的概念覆盖、署名和来源；不能为了压缩篇幅默默删掉后续必需的知识。已有源码变化时清除对应历史输出和执行记录，不让旧实验结果冒充新内容。保留仍被来源清单引用的 ID，或在确有必要时同步映射。

少量剩余代码应能在干净环境执行；声明必须的依赖，避免依赖已删除单元的导入、变量或函数。生成的图保存在项目约定的资源目录，核对标签、数值和正文解释，隐藏绘图实现不等于隐藏学习所需推理。

图片必须在用户实际使用的阅读器中可靠显示。对 notebook 的少量静态教学图，可用 Markdown 单元的标准 attachments 与 `attachment:文件名` 引用，避免编辑器不能解析相对路径。先生成并检查图片，再嵌入同一份字节；检查导出 HTML 中的图像数据，不能只确认磁盘文件存在。不要把历史训练输出包装成改写后新执行的结果。

## 验证与交付

复核手算结果、公式适用条件和前后符号。逐节阅读保留代码，确认首次使用的关键 API 有就近说明，每个有代码的小节都有帮助理解的注释，重复接口只解释新增用法。运行仓库已有结构/链接检查。改动可执行代码、删除依赖单元或改变运行说明时，执行受影响的路径；纯文字编辑先核对代码与来源映射未改变，不为此重跑全部昂贵训练或新建复述文字的测试。有图时查看实际渲染。

批量推广前记录编辑前状态和已确认样节的范围；逐章复核实际段落与相邻代码后修改，不能用统一截断、关键词删句或只加导读代替内容优化。检查原有 ID、锚点、链接、图片及必要来源仍有效，区分本轮增量与工作区已有修改。交付说明实际更新范围和验证边界。

交付时链接实际样章和 skill，简要说明删除了哪类代码、补了哪些解释及验证结果，给出最值得用户先看的小节。不要自行宣称用户已满意。收到反馈后先修样章，再把可复用的偏好写回 skill。
